# RM-E04F — خلاصهٔ اجرایی: معماری اختیار حاکمیتی و انتساب نقش

**DRAFT — NOT APPROVED / پیش‌نویس — تأییدنشده.** این سند فقط معماری و مستندسازی است. هیچ کس منصوب نشده، هیچ
اختیاری فعال نشده، هیچ تأییدی ثبت نشده و هیچ دسترسی (grant) ایجاد نشده است. **Production: NO-GO.**

سند اصلی (انگلیسی): `rm-e04f-authority-role-assignment-architecture.md` — همین پوشه.

## ۱. مسئله

امروز نقش‌های حاکمیتی (مالک فهرست تصمیم‌ها، مالک محصول، فروش، امنیت، حقوقی، مالی، ثبت‌کننده و تأییدکنندهٔ مستقل
T5) فقط در اسناد نام برده شده‌اند و همه **UNASSIGNED** هستند (RM-E04E §1.2). هیچ مدل داده‌ای برای «چه کسی، از چه
زمانی تا چه زمانی، با کدام سند، چه اختیاری دارد» وجود ندارد. استقلال امضاکنندگان در اعتبارسنج R6 فقط با **نام**
سنجیده می‌شود.

## ۲. یافته‌های اصلی ممیزی

| # | یافته | اثر |
|---|---|---|
| ۱ | استقلال با نام نرمال‌شده سنجیده می‌شود؛ «مهرداد حافظی» و نگارش لاتین همان نام، دو نفر شمرده می‌شوند (آزمایش جهشی، §14.2 سند اصلی) | خطر پذیرش دو امضای یک نفر؛ تا پیاده‌سازی شناسهٔ شخص، کنترل انسانی چک‌لیست T5 لازم است |
| ۲ | مدل «شخص تأییدشده» وجود ندارد؛ تصمیم R5-SEC-01 باز است | استقلال واقعی بر پایهٔ شخص فعلاً قابل اثبات نیست |
| ۳ | ریشهٔ اعتماد برای انتصاب (جایگاه مدیرعامل) مدل نشده است | نیاز به تصمیم معماری جدید |
| ۴ | جدول زمانی (`valid_from` / `valid_to`) و قید عدم هم‌پوشانی در پایگاه داده سابقه ندارد | قرارداد جدید پایگاه داده لازم است |

آنچه دوباره استفاده می‌شود: حساب کاربری `identity.user_account`، شخص `organization.person`، درخت واحدها، رکوردهای
R6، ممیزی append-only (`audit.audit_event`)، الگوی «سلسله‌مراتب هرگز دسترسی نمی‌دهد». هیچ سیستم هویت یا مجوز
رقیبی طراحی نشده است.

## ۳. مدل پیشنهادی (خلاصه)

پنج عمل **هرگز یکی نمی‌شوند**:

| عمل | نتیجه | چه چیزی را نتیجه نمی‌دهد |
|---|---|---|
| انتصاب سازمانی (توسط دارندهٔ جایگاه مدیرعامل، با سند) | PositionAssignment | اختیار امضا، دسترسی CRM |
| فعال‌سازی اختیار حاکمیتی (با سند اختیار + تأیید مستقل انسانی) | AuthorityAssignment = ACTIVE | تصمیم، دسترسی CRM |
| امضای تصمیم | DecisionApproval | تأیید T5 |
| تأیید مستقل T5 در R6 | IndependentVerification | پیاده‌سازی یا باز شدن دروازه |
| فعال‌سازی دسترسی production | role_grant فعال (آینده؛ D-42، D-34، Group C) | — |

چرخهٔ عمر اختیار: `NOMINATED → PENDING_AUTHORITY_EVIDENCE → PENDING_VERIFICATION → ACTIVE → EXPIRED / REVOKED`
(+ `REJECTED`، `WITHDRAWN`، `SUPERSEDED`). تنها راه رسیدن به `ACTIVE`، تأیید یک انسان مستقل است.

قواعد استقلال بر پایهٔ **شناسهٔ تغییرناپذیر شخص** است، نه نام حساب یا عنوان نقش: هر شخص حداکثر یک امضا برای هر
نسخهٔ تصمیم؛ تأییدکنندهٔ T5 نه امضاکننده، نه ثبت‌کننده، نه اتوماسیون؛ امضای تفویضی هم جای تفویض‌گیرنده و هم جای
تفویض‌دهنده را اشغال می‌کند؛ هر حساب نامعلوم یا متعارض → `UNKNOWN` / `CONFLICT` → رد.

## ۴. مدل انتصاب توسط مدیرعامل

- مدیرعامل یک **جایگاه** با کلید `CEO` است، نه یک نام. هیچ نامی در کد یا تعریف نقش نوشته نمی‌شود.
- دارندهٔ جایگاه مدیرعامل فقط با سند حقوقی بیرونی (مثل صورت‌جلسهٔ هیئت‌مدیره) و تأیید مستقل ثبت می‌شود.
- **خودانتصابی ممنوع است**: منصوب‌کننده نمی‌تواند خودش را منصوب کند. اگر مدیرعامل بخواهد خودش یکی از سمت‌ها را
  داشته باشد، سند از مرجع بالاتر لازم است (تصمیم معماری RM-E04F-AD2).
- گفتهٔ مالک پروژه («مدیرعامل منصوب می‌کند») به‌عنوان ورودی طراحی ثبت شده، **نه** به‌عنوان سند انتصاب.

## ۵. وضعیت فعلی نامزدی مهرداد حافظی

| سمت | وضعیت |
|---|---|
| مالک فهرست تصمیم‌ها | NOMINATED (نامزد) |
| مالک محصول | NOMINATED |
| مالک فروش | NOMINATED |
| مالک امنیت | NOMINATED |
| مالک حقوقی | NOMINATED |
| مالک مالی | NOMINATED |
| ثبت‌کنندهٔ تصمیم | NOMINATED |
| تأییدکنندهٔ مستقل T5 | **UNASSIGNED** — نیاز به شخص مستقل دیگر |

ثبت در `docs/governance/rm-e04f-authority-nominations.json`. این‌ها **نامزدی موقت** هستند: انتصاب تأییدشده نیستند،
امضای انسانی نیستند و شاهد اختیار نیستند. یک نفر در هفت سمت = **یک** تأییدکنندهٔ مستقل؛ بنابراین حتی پس از فعال‌سازی،
تصمیم‌هایی که امضای مستقل محصول + فروش + امنیت می‌خواهند (مثل M2 رکورد ۱ و ۲ و دروازهٔ Group B) با این نامزدی‌ها
به‌تنهایی **قابل تأیید نیستند**.

## ۶. شواهد باقی‌مانده

1. سند حقوقی تعیین دارندهٔ جایگاه مدیرعامل (و مرجع ثبت آن).
2. حکم انتصاب برای هر سمت (شمارهٔ سند، تاریخ، صادرکننده، دامنه)، صادرشده توسط دارندهٔ جایگاه مدیرعامل — و اگر نامزد
   خودِ مدیرعامل است، از مرجع بالاتر.
3. تصمیم R5-SEC-01 (هویت شخص) برای اتصال حساب به شخص.
4. معرفی یک شخص مستقل به‌عنوان تأییدکنندهٔ T5.
5. اشخاص مستقل دیگر برای نقش‌هایی که باید جدا امضا شوند.
6. بازبینی Codex و Security (وضعیت: **PENDING**).
