# R3 — Staging architecture (disposable reference environment)

**Scope.** A locally reproducible, containerised reference environment for deployment, backup and
disaster-recovery rehearsals with SYNTHETIC data only.
- It is **not** a decision about the production orchestrator.
- Docker Compose was chosen because it is reproducible on any developer host and on CI runners.
- Alternatives (systemd units on a VM, Kubernetes / Helm, a managed PaaS) remain open and are an
  infrastructure-owner decision.

## Topology

```
host 127.0.0.1:8443 (only published port)
        │ TLS (self-signed, per-environment)
        ▼
   ┌──────────┐  edge network
   │   web    │  nginx (pinned digest): verified web bundle, HSTS / CSP headers, /api → api:8080
   └────┬─────┘
        │  internal network (internal: true → no route out)
   ┌────▼─────┐      ┌──────────┐      ┌──────────────┐
   │   api    │      │  worker  │      │  postgres 16 │  volume: pgdata (disposable label)
   │ :8080    │      │ :9091    │      │  :5432       │
   │ :9090 /metrics  │ /metrics │      └──────▲───────┘
   └──────────┘      │ volume: evidence      │
                     └──────────┘            │
   one-shot:  migrate (crm-migrate up) → bootstrap (logins, attestation) ┘
```

## Start-up and shutdown ordering

1. postgres is healthy.
2. migrate completes successfully.
3. bootstrap completes successfully.
4. api and worker start, gated on health checks.
5. web starts once api is healthy.

On shutdown, stop grace periods apply: api 15 s, worker 40 s (above its 30 s drain grace). Restart
policy is `unless-stopped`. Drills #1 and #2 measured recovery after a process crash at about 4 s.

## Required properties

| # | Property | How | Verified by |
|---|---|---|---|
| 1 | No production network connectivity | `internal: true` network; only web joins `edge` | `stage.sh verify` (`internal_egress: blocked` only when the probe first reached an internal service and then failed outbound; a probe that could not run reports `UNKNOWN` and fails the gate); `preflight` |
| 2 | No real external provider credentials | Write-back adapter disabled; provider adapter disabled; no gateway configured | Worker reports 2 jobs BLOCKED |
| 3 | No real customer records | Fresh database; migrations only; synthetic fixtures in tests | Bootstrap creates no data |
| 4 | No shared production volumes | Named volumes labelled `crm.disposable=true` | `destroy` refuses unlabelled volumes |
| 5 | No shared production PostgreSQL cluster | Dedicated postgres container | Compose topology |
| 6 | Explicit staging attestation | Bootstrap sets `worker.environment.staging` and refuses if another environment is attested; workers bind every login to the attested database (R2) | Drill #4; `TestModuleLoginsBoundToAttestedDatabase` |
| 7 | Least-privilege service identities | Containers run as uid 65532, read-only root, no capabilities, no-new-privileges | Compose; image user check in CI |
| 8 | Separate module logins | One `NOINHERIT` login per owner module, plus a read-all backup login | Bootstrap; `db.Runner` refuses shared logins |
| 9 | Deterministic synthetic seed data | Migrations plus deterministic test fixtures (R2 / R3 harness); see limitation below | Tests |
| 10 | Resource limits | CPU and memory limits per service | Compose |
| 11 | Health and readiness checks | `crm-healthcheck` (loopback only) for api and worker; `pg_isready`; nginx `/healthz` | `stage.sh up --wait` |
| 12 | Safe ordering | `depends_on` with conditions (above) | Drill #13: failed migration keeps services down |
| 13 | No automatic business-write activation | Every job switch and flag OFF; bootstrap refuses if any other flag is enabled | `verify`: jobs paused or blocked |
| 14 | No destructive cleanup outside disposable resources | `destroy` requires `CRM_STAGING_DESTROY=crm-staging`; only this project's disposable-labelled volumes | Drill #20 |

**Limitation (seed data).** The compose stack starts with migrations only. Multi-module synthetic data is
generated by the Go test harness (`internal/integration/legacy/shadow`) inside disposable test databases
(backup and restore rehearsals). Loading a synthetic snapshot into the compose stack through
`crm-legacy-import load` is supported by the existing tool but is **not automated in R3**.

## Secrets

Secrets are generated per environment by `stage.sh init-secrets` into `deploy/staging/.secrets/`:
- the directory is gitignored and every file is `0400`;
- each file is owned by the uid that needs it (65532 for the apps, 70 for postgres, root for TLS and the
  provisioning SQL);
- they are mounted as compose secrets and read through `*_FILE` variables.

No secret is placed in an image, a build argument or a plain environment variable; `preflight` enforces
this. TLS uses a 30-day self-signed certificate for `crm-staging.local`.
