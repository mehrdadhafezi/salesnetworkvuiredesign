# ممیزی کامل فایل‌ها و پنل‌ها — نسخه 2.0.12

این نسخه ادامهٔ مستقیم 2.0.11 است و با هدف یکپارچه‌سازی مسیرهای بارگذاری، پیدا کردن اتصال‌های ناقص و آماده‌کردن افزونه برای توسعهٔ بعدی ساخته شده است. هیچ جدول، ستون یا رکورد عملیاتی حذف نمی‌شود و منطق مالی، پرداخت، پیامک، پورسانت و کیف پول تغییر کسب‌وکاری نکرده است.

## ایرادهای اصلاح‌شده

### 1. داشبورد مدیریت در بوت‌استرپ سبک

شورت‌کد `[sn_admin_front_dashboard]` در هسته ثبت شده بود اما از رجیستری بوت‌استرپ سبک جا افتاده بود. در یک صفحهٔ مستقیم فرانت‌اند، این اختلاف می‌توانست باعث شود هستهٔ CRM برای داشبورد مدیریت بارگذاری نشود. رجیستری سبک و رجیستری اصلی اکنون برای هر ۲۶ شورت‌کد همسان هستند.

### 2. تشخیص پنل‌های قرارگرفته در Elementor

تشخیص asset و هسته فقط `post_content` را بررسی می‌کرد. اگر شورت‌کد یک پنل داخل دادهٔ Elementor قرار می‌گرفت، امکان داشت پنل بدون فایل‌های لازم یا بدون بارگذاری هسته اجرا شود. اکنون `_elementor_data` نیز در هر دو مسیر بوت‌استرپ و انتخاب asset بررسی می‌شود.

### 3. ترتیب نصب تازه و ساخت جداول

در فعال‌سازی تازه، ماژول‌های پروژه و Dot ممکن بود قبل از اجرای Migration سرویس HR/MIS فعال شوند. Migration اکنون به‌صورت صریح در activation بارگذاری و پیش از seed ماژول‌های Campaign، Projects و Dot اجرا می‌شود. این تغییر افزایشی و idempotent است.

## دامنهٔ ممیزی ایستا

ابزار مستقل `tools/static-audit.js` بدون وابستگی npm این کنترل‌ها را انجام می‌دهد:

- تطبیق نسخهٔ هدر افزونه با `SN_VERSION`
- وجود همهٔ includeها و assetهای ارجاع‌شده با مسیر literal
- parse شدن هر ۱۵ فایل JavaScript با Node
- توازن ساختاری هر ۹ فایل CSS
- معتبر بودن فراخوانی‌های `$this->method()`، callbackهای هوک و فراخوانی‌های استاتیک کلاس‌ها
- برابری ۲۶ شورت‌کد هسته و بوت‌استرپ سبک
- ثبت بودن شورت‌کدهای ۱۳ مسیر پنل HR و ۱۹ صفحهٔ پورتال
- ثبت بودن actionهای استفاده‌شده در JavaScript، فرم‌ها و PHP
- نبود `DROP TABLE`، `TRUNCATE TABLE` یا `RENAME TABLE` در کد اجرایی
- اجرای `php -l` روی همهٔ فایل‌های PHP، هر زمان PHP CLI در محیط موجود باشد

فرمان تکرار ممیزی:

```bash
node tools/static-audit.js --json
```

خروجی تحویل این نسخه از نظر کنترل‌های قابل اجرا `PASS` است. محیط ساخت فعلی PHP/WordPress/MySQL ندارد؛ بنابراین `php -l` و آزمون واقعی درخواست‌ها باید روی Staging اجرا شوند.

## پنل‌ها و مسیرهای پذیرش

| حوزه | مسیر یا پنل | کنترل اصلی روی Staging |
|---|---|---|
| ورود و مسیریابی | `[sn_login]`، `[sn_unified_login]`، `[sn_my_panel]` | ورود با نقش/سمت و هدایت به پنل اختصاصی |
| مدیریت | `[sn_admin_front_dashboard]` و صفحات مدیریت وردپرس | بارگذاری منوها، آمار و assetها بدون خطای PHP/JS |
| فروش | فروشنده، سرپرست، سرپرست ارشد، مدیر و معاون فروش | محدودهٔ مشتری/دیتا و عملیات مجاز هر سطح |
| سازمان | HR و MIS | لیست نیروها، سلسله‌مراتب، Import/Export و پخش کنترل‌شدهٔ داده |
| مالی | مالی، فاکتور داخلی و فاکتور عمومی | token عمومی، ثبت پرداخت، تأیید/رد و عدم دوباره‌کاری |
| خدمات | خدمات پس از فروش، پروفایل مشتری و گزارش‌ها | محدودهٔ دسترسی و خروجی امن |
| Dot | جریان مشتری، تبدیل‌کننده و فرم مارکتینگ | نگاشت محصول، لینک و دسترسی تبدیل‌کننده |
| پروژه | مدیر پروژه و کارشناس پروژه | تخصیص گروهی، وضعیت، اتصال فاکتور و محدودهٔ پرونده |
| گفتگو | چت، فایل و اعلان خوانده‌نشده | ارسال/دانلود مجاز، شمارنده و صفرشدن هنگام مشاهده |
| کیف پول | «کیف پول من» و دفتر بیاوین | موجودی، سابقه و جلوگیری از ثبت تکراری |

## شرط انتشار Production

1. ZIP روی یک کپی Staging با همان نسخهٔ WordPress، WooCommerce و PHP سایت اصلی نصب شود.
2. `php -l` برای فایل اصلی و همهٔ فایل‌های `includes/*.php` اجرا شود.
3. با هر نقش حداقل یک‌بار ورود و صفحهٔ اختصاصی باز شود و Network/Console مرورگر بررسی شود.
4. یک چرخهٔ آزمایشی فاکتور، پرداخت، تأیید مالی، پروژه، چت، فایل، اعلان و کیف پول تکمیل شود.
5. انتقال HR یک بار Export، سپس Dry-run Import و در پایان Apply روی دادهٔ آزمایشی اجرا شود.
6. error log وردپرس/PHP و گزارش خطای دیتابیس بعد از سناریوها خالی یا بررسی‌شده باشد.

عبور از ممیزی ایستا به معنی سالم بودن wiring و بسته‌بندی قابل‌تشخیص از روی کد است؛ تضمین سلامت عملیاتی فقط پس از عبور از این smoke test در محیط واقعی معتبر است.
